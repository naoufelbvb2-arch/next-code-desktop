# NCD-00 — Next Code Desktop: Project Scope & Requirements

> **Status:** FROZEN — Scope Baseline v1.0 (OWNER APPROVED 2026-10-18)؛ اعتماد نطاق فقط، **وليس إذنًا بالتنفيذ**  
> **Document ID:** NCD-00  
> **Project:** Next Code Desktop  
> **Date:** 2026-10-18  
> **Authority:** اعتمد صاحب المشروع نطاق هذه الوثيقة صراحةً بتاريخ 2026-10-18. أي تعديل لاحق في النطاق يتطلب طلب تغيير وموافقة جديدة؛ لا يُستنتج من الاعتماد إذن بالبرمجة.

## 1. الغرض من الوثيقة

تحديد النطاق الوظيفي وحدود الإصدار الأول من **Next Code Desktop** قبل كتابة المواصفات البصرية والمعمارية أو إصدار تعليمات التنفيذ إلى Antigravity. هذه الوثيقة تصف **ماذا نبني ولماذا**؛ أما **كيف نبنيه** فيُفصّل لاحقًا في NCD-01 وNCD-02 وNCD-03.

## 2. تعريف المشروع

**Next Code Desktop** تطبيق سطح مكتب محلي مخصص للتفاعل مع وكيل البرمجة **Next Code** القائم أصلًا. يوفر واجهة نظيفة لفتح مشروع برمجي، إجراء محادثة مستمرة مع الوكيل حول المشروع، إرسال المهام ومتابعة نتائجها، واستعراض الملفات ومخرجات التنفيذ، ومراقبة الوكلاء المتخصصين من صفحة Agents مستقلة.

ليس الهدف إنشاء وكيل جديد، أو منصة عامة تستضيف وكلاء متعددين، أو إعادة بناء المحرك الحالي داخل التطبيق.

**المستودعات:**
- **المحرك الأصلي (مرجع مستقل):** [`naoufelbvb2-arch/next-code`](https://github.com/naoufelbvb2-arch/next-code).
- **مستودع التطبيق المقترح:** `next-code-desktop` — منفصل عن المحرك، ويُنشأ فقط عند التصريح بالتنفيذ.

**الحقيقة التقنية المتاحة وقت صياغة المسودة:** المحرك مكتوب بـ Python، ويعرض `AgentOS.execute_task()` لتشغيل مهمة وإرجاع نتيجتها. توجد واجهة CLI في `run.py`، لكن لا نعتمد وجود بث أحداث رسومي منظم، أو إلغاء آمن، أو تبديل نموذج من الواجهة، قبل إثبات ذلك في مراجعة التكامل. وتبقى هذه القدرات متطلبات مستقبلية أو مواضع تحقق، لا حقائق منجزة.

## 4. المستخدم والبيئة المستهدفة

- **المستخدم الأساسي في البداية:** صاحب المشروع نفسه، يعمل على جهازه محليًا.
- **نظام التشغيل الأولي (D-03 — DECIDED):** Windows فقط للإصدار الأول، بما في ذلك التطوير والاختبار وحزمة التشغيل الأولية. لا يُطلب دعم macOS أو Linux أو اختباره ضمن هذا الإصدار؛ ويمكن إعادة تقييم دعمهما لاحقًا بقرار مستقل.
- **نموذج التشغيل:** الواجهة والخدمات الوسيطة تعمل محليًا. قد يتصل **محرك الوكيل** بمزود LLM خارجي عند تنفيذ المهام؛ لذا لا يجوز وصف تنفيذ المهام بأنه يعمل دون إنترنت بصورة مطلقة.
- **التوزيع العام:** مؤجل حتى يثبت التطبيق استقراره محليًا.

| FR-03 | إدخال الرسائل | كتابة رسالة وإرسالها ضمن المحادثة الحالية؛ تعطيل أو منع الإرسال غير الصحيح؛ إبقاء النص عند فشل التسليم |

| FR-05 | دورة حياة المهمة | الحالات الظاهرة: جاهز، قيد التنفيذ، نجحت، فشلت. لا تعرض الواجهة نجاحًا قبل ورود تأكيد من المحرك |

| FR-13 | تاريخ المحادثة المحلي | حفظ رسائل المحادثة وحالات المهام وربطها بالمشروع محليًا لاستعادتها بعد إعادة فتح التطبيق، مع عدم الخلط بين سجل UI وذاكرة AgentOS الداخلية |
| FR-14 | محدد النموذج (D-04: B) | يظهر موضع اختيار النموذج **داخل شريط المحادثة** كما في التصميم المعتمد. تعرض القائمة أسماء النماذج المدعومة والمثبتة فعليًا فقط؛ وإذا لم تتوافر إلا تهيئة واحدة قابلة للاستخدام، تُعرض هويتها بوضوح دون الإيحاء بإمكانية تبديل غير موجودة. لا يُسمح باختيار نموذج لا يستطيع المحرك استخدامه. |
| FR-15 | صفحة Agents مستقلة (D-05: B) | يوجد مسار مستقل من Sidebar لعرض الوكلاء المؤقتين التابعين لمحرك Next Code: **Active Agents**، **Agent Status**، **Assigned Task**، **Execution Reports**، **Activity History**. تظهر البيانات الموثوقة فقط، مع حالات فارغة/غير متاحة صريحة، ولا يُعرض التقدم المختلق أو تُنشأ جلسات وكلاء اصطناعية لأغراض العرض الإنتاجي. |

**ملاحظة بشأن Agents (D-05):** الصفحة **إلزامية** في الإصدار الأول ومستقلة عن Chat. وهي مخصصة للوكلاء المؤقتين **داخل Next Code نفسه**، لا لاستضافة مشاريع Agents أخرى. عرض أحداث تفصيلية لحظية **مشروط** بوجود مصدر من المحرك مثبت ومختبر؛ في غيابه يجب أن تظهر حالة «غير متاح» أو سجل محدود بما أمكن إثباته بدل توليد أنشطة مزيفة. تنتهي حياة الوكيل المؤقت بعد مهمته وفق منطق المحرك؛ استمرار عرضه في History يعني حفظ التقرير/السجل فقط، لا إبقاء الوكيل نشطًا.

## 6. الهوية البصرية والتفاعل

الصورة التي اعتمدناها في المحادثة والشعار الجديد هما **مرجعان بصريان** للمواصفة NCD-01، وليسا ملفات CSS أو متطلبات تنفيذ دقيقة بحد ذاتهما.

الثوابت المتفق عليها مبدئيًا:
1. خلفية داكنة بنمط شبكة نقاط مع موجات ضوئية زرقاء وبنفسجية **هادئة**.
2. ألواح شبه شفافة بتأثير frosted / morphing glass؛ توهج محدود لا يؤثر في قراءة النص.
3. شعار Next Code الجديد برمز أزرق وعلامة عمودية، وخط فضي مائل خفيف.
4. Sidebar أيسر يختفي ويظهر بضغطة زر.
5. حقل إدخال رئيسي في الوسط يحتوي **محدد النموذج داخله**، ثم ينتقل إلى أسفل مساحة محادثة تحتوي الرسائل السابقة وتحديثات/نتائج المهام، بدل استبدال كامل الشاشة بمجرد ملخص تنفيذ.
6. Right Dock أيمن بتبويبي Terminal وFiles؛ لا نقط تحكم حمراء/صفراء/خضراء؛ يمكن إخفاؤه وتغيير عرضه؛ مؤشر حالة واحد ذو معنى وظيفي.
7. صفحة **Agents** مستقلة في مساحة العمل الرئيسية عبر Sidebar؛ تحفظ الشاشة الرئيسية والمحادثة بساطتهما، وتقدم مساحة مناسبة لبطاقات حالة الوكلاء وتقاريرهم وسجل نشاطهم، مع بيان مصدر البيانات والتعامل مع الفراغ.
8. تبقى الواجهة عملية عند تصغير النافذة، وتتاح إمكانية تقليل الحركة والوهج.

**قاعدة:** لا يجوز التضحية بالوضوح أو الأداء لصالح المؤثرات البصرية.

## 7. حدود المسؤولية بين التطبيق والمحرك

**Desktop مسؤول عن:** عرض الواجهة وصفحة Agents؛ استقبال رسائل المستخدم؛ اختيار المشروع؛ حفظ/استعادة سجل المحادثة محليًا؛ إدارة نافذة التطبيق وتفضيلات العرض؛ إدارة عملية الاتصال المحلية؛ إظهار الحالات والنتائج؛ حفظ وعرض تقارير نشاط الوكلاء المتاحة (لا حالاتهم الداخلية)؛ القراءة المصرح بها من ملفات المشروع.

**Next Code الأصلي مسؤول عن:** التخطيط، القرارات المعمارية، استدعاء الوكلاء المؤقتين، تنفيذ أدواته المعتمدة، قواعد الحماية، checkpoint / rollback، والتحقق من النتائج.

**الحد بينهما:** Bridge صغير ومخصص لـ Next Code فقط؛ تبادل رسائل منظَّمة مع معرّف محادثة ومعرّف مهمة وحالات وأخطاء واضحة. **لا** نبني Plugin SDK أو Agent Hosting Platform.

**قرار D-04 — محدد النموذج:** `ModelGateway` الحالي يوفر مسارات/ملفات تعريف للنماذج، لكن هذا لا يثبت وجود API عامة لتبديل النموذج عبر Desktop. لذلك يكون محدد النموذج جزءًا من UI المعتمد؛ أما الخيارات الفعلية فتُستمد من الإمكانيات المتحقق منها. ويُحدد في NCD-03 نطاق الاختيار وتأثيره على أدوار الـReasoning والـWorkers وطريقة عرضه بشكل غير مضلل. يُمنع استخدام اختيار شكلي يغيّر النص المرئي فقط دون تغيير إعداد التنفيذ.

**قرار D-02 — الاستمرارية الدلالية للمحادثة:** واجهة `AgentOS.execute_task(task_goal, task_id)` المتاحة حاليًا تعمل وفق مهمة؛ ولا تثبت وحدها امتلاك المحرك سياق حوار متعدد الرسائل. لهذا تُعتبر إدارة سياق المتابعة متطلب تكامل **إلزاميًا** يجب تصميمه واختباره في NCD-03، من دون افتراض أن `Blackboard` هو تاريخ محادثة أو أن عرض رسائل متتالية وحده يحقق محادثة مستمرة. تُفصل هوية المحادثة عن هوية كل مهمة، ولا نغير منطق المحرك الأصلي تلقائيًا.

**قرار D-05 — صفحة Agents مستقلة:** تستمد بيانات الصفحة من تقارير/أحداث يمكن التحقق منها في AgentOS أو من مصدر حالة موثق؛ لا يُعد تحليل سجلات Terminal نصيًا عقد أحداث نهائيًا. يجب الفصل بين «وكيل يعمل الآن» و«تقرير وكيل انتهى»، مع إظهار حالة عدم توفر الحالة الحية بدقة. تفصيل عقود الأحداث والاسترجاع والحفظ في NCD-03.

لا يجوز للواجهة أن تتجاوز صلاحيات محرك Next Code أو تعيد تنفيذ قراراته الأمنية، ولا يجوز اعتبار نافذة Terminal مصدر الحقيقة الوحيد لحالة المهمة.

## 9. خارج النطاق صراحةً (Non-Goals)

- استضافة وكلاء مستقلة متعددة، أو نظام Plugins/Adapters عام.
- إعادة كتابة الطبقات L1–L4 أو تعديل خوارزمية الوكيل.
- بناء محرر IDE متكامل ينافس VS Code في الإصدار الأول.
- تشغيل نماذج LLM محلية أو بناء خادم سحابي من الصفر.
- حسابات مستخدمين، اشتراكات، متجر، تعاون جماعي أو مزامنة سحابية.
- دعم macOS وLinux أو إطلاق عام متعدد المنصات في الإصدار الأول؛ يُعاد تقييم ذلك لاحقًا بعد استقرار نسخة Windows.
- مؤثرات ثلاثية الأبعاد معقدة أو تخصيصات تصميم غير مرتبطة بوظيفة واضحة.

## 10. مسارات الاستخدام الرئيسية

**UC-01 — محادثة ومتابعة مهمة:** يفتح المستخدم التطبيق ← يحدد مجلد المشروع ← يكتب هدفًا واضحًا ← يرسل ← يرى حالة التشغيل ← يحصل على نتيجة موثوقة أو خطأ ← يكتب متابعة مثل «عدّل الحل السابق» في المحادثة نفسها ← يستقبل الوكيل سياقًا صحيحًا بما يسمح بالتعامل مع المتابعة.

**UC-01b — العودة إلى محادثة سابقة:** يغلق المستخدم التطبيق بعد انتهاء المهمة ← يعيد فتحه ← يعثر على رسائل ونتائج المحادثة المرتبطة بالمشروع ← يتابع الحوار من حيث توقف. لا يعني ذلك إمكان استئناف عملية كانت تعمل أثناء التعطل.

**UC-02 — فحص المشروع:** يفتح تبويب Files ← يتصفح الشجرة ضمن المشروع المختار ← يعاين ملفًا للقراءة فقط.

**UC-03 — متابعة التنفيذ:** يفتح `Terminal → Agent Logs` ← يرى سجل المخرجات المتاح ← ينتقل إلى Files دون فقدان حالة المهمة ← يخفي Dock عند الحاجة.

**UC-03b — طرفية المستخدم (حسب مرحلة التنفيذ):** يفتح `Terminal → Interactive Shell` ← ينفذ أوامر في جلسة مستقلة عن الوكيل، وفق مجلد المشروع المحدد وحدود الصلاحيات والإيقاف الآمن. لا يظهر هذا الوضع كميزة قابلة للتشغيل قبل اكتمال متطلباته الأمنية والوظيفية.

**UC-03c — اختيار النموذج:** يرى المستخدم النموذج/التهيئة الفعلية في شريط المحادثة؛ وإذا توفرت عدة خيارات مُثبتة يختار أحدها، فينعكس الاختيار على الطلب الحقيقي وفق عقد التكامل. وإذا لم يُدعَم التبديل بعد، لا يُعرض عنصر تفاعلي يوهم بتبديل النموذج.

**UC-03d — صفحة Agents مستقلة:** ينتقل المستخدم عبر Sidebar إلى صفحة Agents ← يعرض الوكلاء النشطين إن كانت هناك بيانات حية موثوقة ← يفتح تفاصيل المهمة/التقرير المتاح لوكيل SCOUT أو SURGEON أو INQUISITOR ← يرجع إلى Chat دون ضياع المحادثة. إذا لم توجد بيانات أو لم تتوفر أحداث لحظية، تُعرض حالة فارغة/تقييد معلوم؛ لا تعتبر تقارير الوكلاء المنتهين عمليات نشطة.

**UC-04 — غياب المحرك:** يفتح التطبيق دون إعداد Python/Next Code ← تظهر رسالة إعداد واضحة ← يمكن استخدام الواجهة التجريبية دون الإيحاء بتنفيذ حقيقي.

## 11. معايير قبول الإصدار الأول

لا يُقبل الإصدار الأول إلا إذا ثبت الآتي عمليًا على جهاز التطوير:

1. التطبيق يفتح ويغلق بصورة سليمة **على Windows**، وتعمل عناصر التنقل وإخفاء/إظهار اللوحات؛ لا يشترط اجتياز اختبارات macOS أو Linux في الإصدار الأول.
2. يمكن تحديد مجلد مشروع صالح؛ وتُرفض المسارات غير الصالحة مع رسالة واضحة.
3. يمكن إرسال مهمة حقيقية واحدة على الأقل إلى المحرك الأصلي دون تعديل قراراته الداخلية، ثم إرسال **متابعة مرتبطة بنفس المحادثة** تثبت أن السياق السابق يؤثر في فهم الطلب الجديد كما ينبغي.
4. تعرض الواجهة نهاية المهمة الحقيقية (نجاح أو فشل) وتعيد السيطرة للمستخدم بعد خطأ الاتصال.
5. لا تظهر مزايا مستقبلية وكأنها مكتملة؛ تكون معطّلة أو موصوفة بوضوح. يظهر محدد النموذج في شريط المحادثة، لكن لا تُعرض خيارات تشغيل إلا إذا أثبتت اختبارات التكامل دعمها فعليًا.
6. يمكن معاينة الملفات المصرح بها فقط، دون كشف الأسرار أو تجاوز حدود المشروع.
7. تجتاز اختبارات الواجهة والعقد والجسر المعتمدة، ويُرفق تقرير بالنتائج الفعلية وما لم يُختبر.
8. يُثبت أن المستودع الأصلي لم يتغير أثناء تنفيذ Desktop.
9. يبقى تاريخ رسائل المحادثة قابلاً للاسترجاع بعد إعادة فتح التطبيق، وتبقى هوية المحادثة مستقلة عن معرّفات مهام التنفيذ.
10. يمكن فتح **صفحة Agents مستقلة** من Sidebar، وتوضح حالة كل وكيل والمهام والتقارير وسجل الأنشطة **حين تتوفر أدلة موثوقة**، أو تعرض حالات «لا يوجد نشاط / بيانات حية غير متاحة». لا يُقبل نجاح الصفحة استنادًا إلى بيانات Mock غير معلنة في نسخة الإنتاج.

## 15. FFR-01 — المراجعة النهائية لنطاق الإصدار الأول

### 15.1 نتيجة المراجعة

**التقييم النهائي: OWNER APPROVED — SCOPE FROZEN v1.0؛ وليس إذنًا بالتنفيذ.** جميع قرارات النطاق الخمسة D-01 إلى D-05 حُسمت. فصل التصميم عن المحرك قائم، ومستودع Desktop سيبقى مستقلًا. لا توجد ضرورة لإعادة فتح الخيارات التي وافق عليها صاحب المشروع.

| مجال المراجعة | التقييم | الضبط المطلوب لاحقًا |

### 15.2 بوابات إلزامية قبل التكامل الفعلي

1. **Conversation Gate:** تحديد آلية لحفظ المحادثات والربط بين `conversation_id` و`task_id` ونقل سياق الرسائل اللاحقة إلى المحرك مع اختبار متابعة حقيقية من رسالتين على الأقل. لا يكفي تخزين التاريخ المرئي.
2. **Agent Activity Gate:** إثبات مصدر كل معلومة معروضة في صفحة Agents؛ يجب التمييز بين Agent يعمل فعليًا وبين تقرير Agent انتهى، وإذا لم يوفر المحرك الحدث تعرض الواجهة حالة غير متاحة. لا يُسمح باستنتاج نشاط لحظي من التخمين.
3. **Terminal Security Gate:** فصل Agent Logs عن Interactive Shell؛ لا تُفعّل الطرفية التفاعلية قبل تحديد حدود العمل والصلاحيات وواجهة PTY وسلوك الإغلاق والتنظيف على Windows.
4. **Model Authenticity Gate:** أي اختيار نموذج يظهر قابلًا للتبديل يجب أن يغيّر المسار المستخدم فعليًا في المحرك؛ غير ذلك يُعرض فقط النموذج/التكوين الحالي بوصفه معلومة.
5. **Repository Integrity Gate:** تنفيذ Desktop في المستودع الجديد فقط؛ أي تغيير مطلوب للمحرك الأصلي يحتاج وثيقة وتصريحًا مستقلين.
